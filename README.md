# Nori 后端（Java 重写版）

用 **Spring Boot 4 + WebFlux** 重写 Nori 的入口层（原 `4173 nori_proxy.js`）。

> **前端一行不改。** MF-Dust 的 Nori.Web + 8 个注入脚本是唯一不可变契约——
> 它们怎么调接口、怎么读帧、怎么发命令，本项目就必须怎么实现。

---

## 这是什么

原来那 7000 行 Node 代理同时干着 **WS 双向透传、台词引擎、语音队列、摸头判定、
生命周期状态机、四个游戏的行为劫持**。所有状态挂在两个全局变量上，任何一处改动都要重新推演整条链。

Java 版把它拆成职责清晰的模块，**并且把每个进程边界都写成可测的类型**：
卡带状态机、帧流驱动、节奏闸门、台词队列各管一段，互不穿透。

- **不绕过**任何付费、鉴权或访问限制

## 为什么重写（最重要的一节）

> **不是为了把 JS 逐行翻译成 Java。**

重写的目的是 **修掉 JS 里的问题 + 拿到扩展性与可维护性**。
所以抄任何一段旧逻辑之前，先判它是「意图」还是「bug」：

| 判据 | 处理 |
|---|---|
| 注释写「原来…导致…」「修正」「★坑」 | 抄**修好的那版**，别抄被改掉的样子 |
| 行为怪，但注释解释了「为什么必须这样」 | **意图** ⇒ 必须保留 |
| 行为怪且无解释 / 明显笔误 | **bug** ⇒ 在这里修掉，并写测试钉死 |
| 旧代码靠「轮询 + 兜底 + 重试」绕过 | 用**结构**解决（事件驱动、明确状态机） |

已经修掉的旧问题（不要抄回来）：

- 象棋的「吃子」判据读了个对象字符串，导致那枚判定**从未真正触发过**
- **「抢跑」**：拿到大脑回复立刻发指令 ⇒ 动画没播完她就出手；指令太密时前端**丢掉过渡**
  （`gameState` 推进了、界面停在旧状态，看起来像"卡死"）
- 蛋糕对决的思考时间盖不住质疑揭示动画（前端实测约 4 秒）
- 靠「本地假 AI + 停掉它」绕协议问题

必须保留的旧意图：寻宝猜完必收手、格挡过牌回攻击相位、你画我猜的底色是**纸色不是白色**。

## 快速开始

### 前置：三个上游要先起来

本服务只替换入口层，其余三个进程原样保留：

| 端口 | 是什么 |
|---|---|
| `4174` | 游戏 exe（静态资源 + 卡带引擎） |
| `8880` | TTS 服务 |
| `25503` | 人格 / 记忆 / 大模型 |

浏览器连 **4183**（本项目），本项目再转发给它们。

### 构建与运行

```bash
./gradlew build          # 编译 + 全部测试
./gradlew bootRun        # 启动（默认端口 4183）
./gradlew test           # 只跑测试
```

端口在 `config/nori-backend.json` 里改，或用**环境变量** `NORI_PORT` 覆盖
（是环境变量，不是 `-D` 系统属性——这两个在本项目里是不同的通道）。
**注意本机若设了 `SERVER__PORT` 环境变量，它会把端口顶掉**——排查"配置了 4183 却起在别的端口"时先查它。

### 打开游戏驱动

帧流驱动默认**关闭**（它会替角色向上游发指令，判错就是污染对局）。开启方式：

```
-Dnori.game.driver=on
```

在 IDEA 里加到 **VM options**（不是 Program arguments——加错位置时 `System.getProperty` 读不到，
启动日志会显示 `driver: nori.game.driver=<未设置>`）。

配套的节奏参数：

```
-Dnori.game.think.chess=2600     # 象棋"想棋"下限
-Dnori.game.stepMs=2200          # 多条指令之间的间隔
-Dnori.game.afterRevealMs=3600   # 质疑揭示动画静默窗口
```

### 管理页

启动后打开 **`http://127.0.0.1:4183/admin`**：上游健康、驱动开关、生效配置、存档列表。

## 架构一页

```
浏览器 ──► 4183 nori-backend (Spring Boot 4 + WebFlux) ──► 4174 exe
              │  ├── /v1/*     ──► 25503 persona
              │  └── /nori-tts ──► 8880 TTS
              └── /nori-* + /api/admin/* 自有业务
```

**为什么是模块化单体**：所有玩法状态（台词进度、语音队列、生命周期、卡带）都围绕
**同一个会话**，拆进程只会把「一次状态变更」变成跨网络事务。等边界稳定再谈拆。

三条不能违反的规则：

1. **每会话一个串行 loop**。绝不在这个线程上阻塞等待（睡一下就冻住台词上屏与音频推帧）。
2. **WS 文本帧不做 JSON 重序列化**，二进制帧零拷贝。
3. **写文件先读旧 → 算新 → 临时文件 → 原子替换**。

## 四个游戏

| 卡带 | 她做什么 | 触发点 |
|---|---|---|
| 国际象棋 | 走子 + 应答悔棋/和棋 | 下行局面里的轮次 |
| 蛋糕对决 | 宣称 / 格挡 / 过牌 | 下行相位 + 行动者 |
| 森林寻宝 | 按提示词翻牌 | 下行回合记录 + **上行提示词** |
| 你画我猜 | 看玩家的画猜词 | **上行笔画**（服务端不回传画面） |

象棋的走法生成是**自己写的**（不引第三方库），正确性由 perft 证明：
初始局面 4 层 197281 节点、经典测试局面 3 层 97862 节点，全部对上。

细节（每个卡带的判定条件、易错点、**实测的真实帧结构**）见 [`docs/GAME_DRIVERS.md`](docs/GAME_DRIVERS.md)。

## 目录

```
src/main/java/net/siniplise/noriosbackend/
├── app         启动、Spring 装配、会话编排
├── admin       /api/admin/*（配置 / 健康 / 存档），前端不感知
├── config      配置层：JSON 三层来源 + 环境变量
├── contract    前端契约：路径、端口、DTO（这里是「前端一行不改」的边界）
├── gateway     HTTP + WS 入口；双向透传
├── runtime     线程模型：每会话串行 loop + 邮箱
├── lifecycle   生命周期状态机（演出 ↔ 游戏 ↔ 离开）
├── script      台词引擎（fact → beat）
├── speech      语音队列 + TTS 调度
├── game        四个卡带的规则与驱动
│   ├── chess / cakeduel / codenames / pictionary
│   └── driver  ★帧流驱动：判断该谁动、发指令、节奏闸门
├── persona     人格服务客户端
├── save        存档
└── obs         日志与可观测性
```

## 已知限制

- **四个卡带的真机验证只做了象棋与森林寻宝（猜牌）**；蛋糕对决、你画我猜尚未真机跑通
- 森林寻宝的「她给提示词」路径**未实现**（答案地图 `key` 已确认可用，缺的是提示词生成）
- 蛋糕对决的 special 卡（牧师/天使等）**刻意未实现** —— 官方自己也没开这套
- 部分 `gameState` 字段名来自源码推断，尚未全部用真实帧核对
